## 1. Step 0 survey and departures from the original Step 5 spec

The Step 0 survey (posted and confirmed before any code was written) covered: the exact
`exit_logic.py` evaluation order and thresholds; that `current_mc` is already fetched once
per cycle for every open position in `runner.py`'s `_monitor_once()` (`market_caps =
await market_data.fetch_market_caps(...)`, line 873) and reused per-position at line 898,
so no new network call is needed; hold-duration statistics from the 64-position sample
(median 12.0 min ≈ 144 cycles at the 5s poll, heavily right-skewed by one 8.6-day outlier);
and `data_logger.py`'s existing `_write()` pattern (stamp `ts`/`run_id`/`schema_version`,
append one JSON line, catch `OSError`/`(TypeError, ValueError)` around the write so a
failure never propagates).

**Six confirmed departures from `EXIT_ANALYSIS.md`'s original Step 5 spec, all approved
before implementation:**

1. **Peak-lag fix.** The spec's proposed call site logs before `exit_logic
   .check_exit_conditions()` runs (that function is what actually updates
   `position["peak_mc"]`), so the stored field would read one cycle stale on any row where
   `current_mc` is itself a new high. Fixed by logging `max(position["peak_mc"],
   current_mc)` directly, which is correct regardless of call-site ordering.
2. **Added `initials_taken`** to the record — required by this brief's own Step 1, absent
   from the original spec.
3. **`SCHEMA_VERSION` bumped 2 → 3**, with a `SCHEMA HISTORY` docstring entry, consistent
   with how the Jupiter-field addition (v2) was recorded.
4. **The ~50 MB/day volume figure was stated explicitly** rather than left as the original
   spec's unquantified "~60x the snapshot heartbeat."
5. **Post-initials only.** Before initials, no trailing stop is active at any drawdown
   setting, so a pre-initials row cannot inform the stepped-stop question and is not
   logged. **This forecloses one kind of analysis**, stated plainly: `price_history.jsonl`
   can never be used to study entry-side behaviour — e.g. how close a position got to
   stop-loss or the absolute floor before ever reaching (or failing to reach) initials.
   That question would need a different, unfiltered log; it was explicitly out of scope
   here.
6. **Trimmed record schema.** Dropped `run_id`, `event`, and `ticker` from this file only
   (kept on the other three). Checked first whether anything relies on `run_id` for
   analysis: neither `exit_analysis.py` nor `entry_analysis.py` reference it anywhere —
   confirmed by grep before dropping it. `schema_version` was kept as instructed.

## 3. Record format

**File:** `data/price_history.jsonl`. **Written:** once per open position per monitor
cycle, only once `initials_taken` is true for that position (section 1, point 5).

**Fields:** `ts`, `schema_version`, `contract_address`, `mc`, `peak_mc`,
`initials_taken`.

**One real example line** (generated by calling `log_price_point()` directly against a
scratch directory, not from any real trading data):

```json
{"ts": "2026-08-28T08:10:03.846011+00:00", "schema_version": 3, "contract_address": "JLsJo64ou3YRzvdHmMkq2WN9RSAHSxUKVy4UuSapump", "mc": 210000.5, "peak_mc": 210000.5, "initials_taken": true}
```

## 4. Estimated file growth at 10 concurrent positions

`MAX_CONCURRENT_POSITIONS=10` in `.env.example` — the number the brief specified is also
the real configured cap, not an arbitrary planning figure.

**Record size:** measured directly via `json.dumps()` on a representative record —
**210 bytes/line** (down from an un-trimmed 290 bytes/line for the original six-field
spec).

**Row rate:** at 5s polling, 10 positions sustained produce 172,800 raw monitor-cycles/day
if every cycle were logged. Restricting to post-initials cycles only, using the 64-position
sample's real fills.jsonl timestamps (initials-fire time to close, versus open to close):

- 20 of 62 fills.jsonl-covered positions ever took initials at all; among those, the
  post-initials segment was a median 71.8% of that position's own remaining lifetime.
- Turned into a share of all position-cycles two ways: **3.71%** including one 8.6-day
  outlier (`Bo`, a position that never took initials and sat open dragging the denominator
  up without contributing to the numerator), or **19.67%** excluding it as unrepresentative.

| basis | rows/day | MB/day | MB/week |
|---|---:|---:|---:|
| including the `Bo` outlier (conservative floor) | 6,411 | 1.28 | 9.0 |
| excluding the outlier (planning estimate) | 33,990 | **6.81** | **47.7** |

Both bases are well under the 15 MB/day gate this stage was told to stop at, so
implementation proceeded without pausing. **6.81 MB/day (≈48 MB/week) is the number to
plan around** — down roughly 7x from the original un-gated, un-trimmed ~50 MB/day estimate.

## 8. What this enables that Stage 6 could not do

Stage 6's Step 4 could not honestly simulate any stepped trailing-stop rule for a position
whose peak multiple crossed the rule's tightening breakpoint, because `peak_mc` is a
running maximum with no timestamp and no record of the price path between logged points —
a tighter stop could have exited earlier, at a market cap the logs never captured. Once
this logging has run for a few weeks on new positions, `price_history.jsonl` gives a
timestamped `mc` reading roughly every 5 seconds for the entire post-initials life of each
one. That is exactly the missing ingredient: for any candidate stepped rule, the exact
market cap and moment the rule would first breach its tighter threshold can be read
directly off this file, rather than inferred from `peak_mc` alone — turning Stage 6's
"not simulable" findings (8 of 62 for Rule 1, 3 of 62 for Rule 2, 21 of 62 for Rule 3) into
answerable ones, for positions opened after this logging exists. It does **not** help with
the pre-initials scope Stage 6 didn't need either (stop-loss/absolute-floor behaviour) — see
section 1, point 5 — and it does **not** retroactively help the 64 positions already in
`positions.json`, which remain exactly as unsimulable as Stage 6 found them.
